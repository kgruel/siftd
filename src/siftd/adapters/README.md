# siftd.adapters

Each module here is the translation layer for one coding tool: it reads that tool's raw log format and produces siftd's domain `Conversation` objects. Adapters own parsing only — they never touch the database or the storage layer, and they never depend on `api/`, `cli/`, or `serve/`. Shared authoring helpers (file discovery, JSONL loading, tool-call linking, the record folds for peek) live in [sdk.py](sdk.py), and peek built from assembled conversations lives in [peek_projection.py](peek_projection.py); the interface contract is defined and enforced in [validation.py](validation.py); [template.py](template.py) is the blank starting point copied by `siftd copy adapter template`.

The interface is a set of module-level attributes, not a base class, and [validation.py](validation.py) is its one definition: the registry, the drop-in check in `siftd doctor` and the architecture tests all read it. Two versions load. **Version 2 (decoding)** is the interface: an adapter sets `ADAPTER_INTERFACE_VERSION = 2` and exports `NAME`, `DEFAULT_LOCATIONS`, `DEDUP_STRATEGY` (`"file"` or `"session"`) and `HARNESS_SOURCE`, plus the callables `discover()`, `can_handle()`, `read(source)` (yields each raw unit) and `decoder(source)` (a `Decoder`, or a class taking the source). **Version 1 (legacy)** exports `parse(source)` instead and builds its own conversations; it keeps loading unchanged, but it has no records to count, so it has no ledger (`gemini_cli`, removed in 0.13.0, is the one built-in left on it). `SUPPORT_TIER` is optional and defaults to `"contrib"` — the `core`/`contrib`/`frozen` tier sets format-tracking expectations, shows up in `siftd adapters`, and scopes parse-error warnings for non-core adapters. The other optional hooks are part of the contract and type-checked when present: `default_session(source)`, `change_paths(source)`, `peek_read(source)`, `peek_enrich(path, scan)`, `SUPPORTS_LIVE_REGISTRATION`, `SUBAGENT_PATH_MARKER`, `PEEK_GLOB_PATTERNS`, `SUPPORTS_PEEK`, `PEEK_LAST_OF_MANY`, `SESSION_ID_IN_PATH`, `TOOL_ALIASES`, `TOOL_HINT_KEYS`, `HARNESS_LOG_FORMAT`, `HARNESS_DISPLAY_NAME` (see [writing-adapters](../../../docs/guides/writing-adapters.md#optional-hooks)). Two invariants are easy to break. The first is per-strategy: a `"file"` adapter's source may yield at most one conversation (ingestion fails the source otherwise, and `tests/architecture/test_dedup_cardinality.py` fails the fixture first), while a `"session"` adapter's source is a container and may yield many — pick `"session"` whenever one source grows new conversations over its life, whatever its storage format. The second: raw tool names must be mapped to canonical `category.action` forms via `TOOL_ALIASES` so cross-tool queries work. The registry is not hardcoded — built-ins are imported here, but drop-in adapters in `~/.config/siftd/adapters/` and entry-point packages are auto-discovered, so add capability through the interface rather than a central list.

**Decode, don't assemble.** An adapter's only tool-specific job is decoding: a reader yields raw units, and a decoder turns each into the canonical records in [records.py](records.py). [assembly.py](assembly.py) does the rest once for every adapter: it decides where each record attaches, merges streamed chunks of one message, pairs tool results with their calls in either order, places a response that precedes every prompt in `Conversation.preamble` (stored with no parent), and gives every record exactly one disposition in a ledger. A decoder never drops a unit silently: it returns `Ignored(reason)` for a deliberate skip, and anything it returns nothing for is counted `Unknown`. [contract.py](contract.py) is where the framework derives what a decoding adapter does not write: `parse()` and `assemble()` (which also returns the ledger, so ingest counts what it already parses), the `Harness`, and the peek hooks (`peek_projection.make_peek_hooks_from_decoder`), so peek and ingest classify each record once. The registry hands consumers a `DecodingAdapter` wrapping each version-2 module, which is why built-ins define none of `parse`, `HARNESS` or the peek hooks (`tests/adapters/test_contract.py` holds the list of the explicit ones, shrink-only). Code that holds a bare module and wants `parse()` calls `contract.adapt(module)`. The record folds in `sdk.py` serve only version-1 adapters, and they leave with that interface (`V1_INTERFACE_REMOVAL` in [`api/compat.py`](../api/compat.py)), together with the SDK helpers a legacy `parse()` builds with.

See [Adapters](../../../docs/concepts/adapters.md) for the conceptual model and tier semantics, and [Writing Adapters](../../../docs/guides/writing-adapters.md) for the full implementation guide including optional peek hooks.
