# siftd.ingestion

This package coordinates the ingest pipeline; it does not parse formats and does not write rows. [discovery.py](discovery.py) fans out across every enabled adapter to find candidate source files, and [orchestration.py](orchestration.py) runs the discover → dedup → `parse()` → store sequence, delegating the actual format parsing to `adapters/` and the actual persistence to `storage/`. For an adapter that decodes, the parse is `assemble()`, which returns the conversations *and* the ledger of what became of every record: ingest adds the ledger's unknown, orphan and ignored counts to `IngestStats.by_harness` (and each `IngestEvent`) from the same parse that is stored, and counts only a parse whose result is stored, so a source read again to check its identity is not counted twice. The layering matters: keep tool-specific logic in adapters and SQL in storage, so this folder stays a thin coordinator.

The invariant to protect is that a source's *cardinality* matches the `DEDUP_STRATEGY` its adapter declares, because `ingested_files.path` is `UNIQUE` and a row can therefore name at most one conversation. A `"file"` source produces one conversation and the row points at it; orchestration fails a `"file"` source that yields more, rather than silently dropping data. A `"session"` source is a *container* — a SQLite database of chats, or a markdown history every session is appended to — and its row is a hash/mtime marker with `conversation_id = NULL`, so each conversation is deduped independently by `external_id` and replacing one cannot cascade the marker away. Pick `"session"` whenever one source holds or grows several conversations, whatever its storage format: `aider` did not, and every history file past its first session failed permanently (#36). Within a container, `ended_at` is the per-conversation change detector — a session reporting none is read as still open and re-stored whenever the file's content changes, which is why an adapter should emit one wherever its format can bound a session. Where an end time cannot show a change (a message stamped before the session's last update), a session may state a `content.revision` attribute; ingest replaces the stored copy when the revision differs and both copies were read from the same source path, which ingest names as `content.source`. A digest orders nothing, so a copy from another source competes on `ended_at` alone. Ingest is idempotent: files whose hash matches a prior run are skipped, so re-running is safe and cheap. `--reparse` is the one deliberate exception: it re-parses every stored source through the same replacement path, so an adapter fix reaches rows that were never going to change. It declines any replacement that would lose a user-applied tag (named by id, counted by `unrestorable_user_tags` in `storage/replacement.py`) unless `--force` is given, through one decision, `_declined_for_tags`, asked about what the plan would remove: a delete counts every assignment on the row, and a split of a row another path claims counts only the event assignments it releases and the incoming parse cannot restore. In a session container it still arbitrates by `ended_at` (latest wins, and a moved `content.revision` from the same source also replaces), so a reparse never replaces a stored session with an older copy from another source. Disabled adapters (via config) are excluded from discovery here, which is why the skip is visible at ingest time.

An adapter that re-keys its conversations names the old ids as `Conversation.superseded_external_ids` (a `Session` states them, for session sources). A row under one of those ids is a candidate when every prompt it stores is one of the conversation's own prompts (responses are not evidence: generic replies are shared across sessions); a prompt is matched by id, else by text with its time, so one prompt typed in two sessions a month apart is not the same message. A candidate is adopted, carrying only that key's queued tags over, unless the evidence is ambiguous (`_adoption_is_ambiguous`). A superseded key is retired: no current parse produces it, so a row holding the transcript is an earlier read of this file. An id an adapter states as `Conversation.inherited_external_ids` is not: codex_cli's restated parent id is also the parent's own key, and a fork holds its parent's prompts, so no amount of prompt containment (equal sets included) separates the parent's row from the fork's; such a row is adopted only when it also began when this conversation began, which a fork's file never does. A bookkeeping pointer at a row under one of these keys is judged the same way, since a legacy collision pointed a fork at its parent's row. An ambiguous candidate keeps its row and assignments, the conversation is stored beside it, and the run reports it (`IngestStats.refused_adoptions`, a warning line from `siftd ingest`): ownership never moves on ambiguous evidence. A session source's parse also receives `Source.metadata["recorded_locations"]`, every path the bookkeeping recorded for the harness: a re-key that depends on how a path was spelled (aider's relative scan roots) reads its old spellings there, because the spelling is not recoverable from the file alone. Only a spelling that can name this file is a candidate, whether recorded or generated from the file's ancestors (`adapters/sdk.py::spells`): another project's absolute path, or `proj/...` where it resolves to another project, is that project's own key, and a copy of its history holds its prompts.

**One plan, one executor.** Every conversation a source yields is stored the same way, whichever branch it came through: `_find_target` takes the write lock and names the stored row at stake (the row under the parse's own key, since the conversation can only be stored in its place; else the bookkeeping pointer; else a superseded or inherited candidate), `_plan` decides what storing does to it (store, replace, split, settle as a copy, link, refuse as ambiguous, or decline for tags), and `_execute` applies that plan. Because the own key is resolved under the lock before anything is stored, a store never collides with an existing row: the duplicate-collision handler in `ingest_all` is left only for a fault, and a new file whose key already holds a row is linked by the plan, from the one parse. The branches keep only their differences: when a source is eligible (a file whose bytes changed, a session that moved, per `_session_should_replace`) and which bookkeeping row it writes. A decline wrote nothing, so the file branch rolls back at once rather than holding the write lock into the next source. `tests/architecture/test_replacement_carry.py` holds the population: assignments are removed only in `_execute`, a plan is made only in `_plan`, and `_plan` asks the tag gate. The door was spelled in five places before, and the session branch's copy had lost its refusal half.

Two invariants govern the replacement itself. First, **a conversation replacement carries what the transcript cannot supply** — see [`storage/replacement.py`](../storage/replacement.py) for what that is and why. Here the thing to know is the shape: snapshot before the delete, re-attach after the insert, in the same transaction (`_take_conversation_for_replacement` / `_restore_carryover_after_replacement`), and the ratchets are keyed on **replacement trigger**, not dedup strategy. A strategy is not what triggers a replacement, and keying on it asserted survival for one trigger while reading as coverage of all of them — which is how #54's ownership loss reached every path without anything failing (`tests/test_live_tagging.py::TestReplacementCarriesWhatTheTranscriptCannotSupply`, guarded by `tests/architecture/test_replacement_carry.py`). What a snapshot cannot carry it still counts, and what it counts it reports: a replacement that parses to nothing names every kind of assignment it was holding, including the ones (block tags, synthetic events) that were never re-pointable. Second, **a queued tag is consumed only once it has been applied** — the drain resolves targets first and leaves the rest in `pending_tags` for the next ingest or for `siftd doctor fix --pending-tags`, because deleting a queued tag is data loss, not a repair. Both the drain and that doctor path resolve targets through `storage/sessions.py`'s `_resolve_pending_target`, so they cannot disagree about where a session tag lands.

A third invariant governs the bookkeeping itself: **a valid conversation pointer is never discarded.** `ingested_files.conversation_id` is the only link from a source file to what it produced, so clearing it strands the conversation and — because a NULL pointer makes the next re-ingest skip its delete and collide again — freezes that file permanently. Every failure path rolls its transaction back first, which resurrects the conversation the re-ingest branch had already deleted, so "this run failed" is never evidence that nothing belongs to the path: the error is recorded and a pointer that still resolves is kept. Only a path that never produced a conversation records NULL. A store that failed *because* the conversation already exists does not route to the error writer at all; it re-points the row at that conversation.

Two corollaries fall out of that. **The row never asserts content it did not ingest**: a link (the plan's, or the collision handler's) leaves `file_hash`/`file_mtime`/`file_size` at whatever was actually stored (a never-matching sentinel when there is no row) rather than stamping the bytes it just hashed for a conversation some other read produced — stamping them makes the unchanged-file skip match forever, which is a silent freeze dressed as a success. And **a row carrying an error is re-examined every run**, whatever its stat says, because the error write stamps the failing file's own stat; without that, a transcript that stops changing after a failure hides behind the skip and the self-heal below is unreachable for exactly the population that needs it.

Neither is the row believed on the way in. The re-ingest path re-derives the truth from the parsed conversation's `(harness_id, external_id)` rather than trusting a NULL, which is what lets rows poisoned by older versions heal themselves — and why that healing must snapshot tags first, since in the poisoned state the orphan is where the tags live. Ownership of a legacy row is decided by its transcript, never by its claim: a claim says who may touch the row, and a row holding another session's transcript (a forked child filed under its parent's id by a legacy release) is adopted or split off only by the conversation whose prompts it holds, so its tags move to that conversation and stay put when more than one claimant holds the same prefix. What it must not do is assume the conversation it finds is unowned: `conversation_id` has no uniqueness constraint and is `ON DELETE CASCADE`, so two paths can carry one session (a restored backup, an overlapping `--path`, or the collision repair's own re-link) and deleting that conversation would take the other path's row and its events with it. So `_plan` replaces only a row no other path points at, and `_take_conversation_for_replacement` checks again before it deletes; a claimed row in a file source is settled against (this file is a copy) or split from (it is not). A session source's bookkeeping never points at a conversation, so a pointer at one from another spelling of the same file is a file-strategy leftover (pre-#36 aider): the plan clears it and replaces, or the session would stay frozen under a key no parse produces again. A pointer from a path that is not a spelling of this file is another file's claim, and the session settles or splits against it as a file source would. A duplicate copy is linked, warned about, and left settled rather than replaced: it records the bytes it has (so the copies do not churn and the warning fires once per change, not once per run) but its content is never ingested, because only the path holding the session's slot may write that conversation. Ingest runs under a per-database advisory lock (`api/ingest.py`) so the race that produced those rows cannot recur; a second concurrent invocation is a quiet no-op, not an error — and a filesystem that refuses the lock degrades to running unlocked with a warning, never silently.
