# siftd.ingestion

This package coordinates the ingest pipeline; it does not parse formats and does not write rows. [discovery.py](discovery.py) fans out across every enabled adapter to find candidate source files, and [orchestration.py](orchestration.py) runs the discover → dedup → `parse()` → store sequence, delegating the actual format parsing to `adapters/` and the actual persistence to `storage/`. The layering matters: keep tool-specific logic in adapters and SQL in storage, so this folder stays a thin coordinator.

The invariant to protect is that a source's *cardinality* matches the `DEDUP_STRATEGY` its adapter declares, because `ingested_files.path` is `UNIQUE` and a row can therefore name at most one conversation. A `"file"` source produces one conversation and the row points at it; orchestration fails a `"file"` source that yields more, rather than silently dropping data. A `"session"` source is a *container* — a SQLite database of chats, or a markdown history every session is appended to — and its row is a hash/mtime marker with `conversation_id = NULL`, so each conversation is deduped independently by `external_id` and replacing one cannot cascade the marker away. Pick `"session"` whenever one source holds or grows several conversations, whatever its storage format: `aider` did not, and every history file past its first session failed permanently (#36). Within a container, `ended_at` is the per-conversation change detector — a session reporting none is read as still open and re-stored whenever the file's content changes, which is why an adapter should emit one wherever its format can bound a session. Ingest is idempotent: files whose hash matches a prior run are skipped, so re-running is safe and cheap. Disabled adapters (via config) are excluded from discovery here, which is why the skip is visible at ingest time.

Two invariants govern the replace paths, which every dedup strategy has its own copy of. First, **a conversation replacement carries what the transcript cannot supply** — see [`storage/replacement.py`](../storage/replacement.py) for what that is and why. Here the thing to know is the shape: snapshot before the delete, re-attach after the insert, in the same transaction (`_take_conversation_for_replacement` / `_restore_carryover_after_replacement`), and the ratchets are keyed on **replacement trigger**, not dedup strategy. A strategy is not what triggers a replacement, and keying on it asserted survival for one trigger while reading as coverage of all of them — which is how #54's ownership loss reached every path without anything failing (`tests/test_live_tagging.py::TestReplacementCarriesWhatTheTranscriptCannotSupply`, guarded by `tests/architecture/test_replacement_carry.py`). What a snapshot cannot carry it still counts, and what it counts it reports: a replacement that parses to nothing names every kind of assignment it was holding, including the ones (block tags, synthetic events) that were never re-pointable. Second, **a queued tag is consumed only once it has been applied** — the drain resolves targets first and leaves the rest in `pending_tags` for the next ingest or for `siftd doctor fix --pending-tags`, because deleting a queued tag is data loss, not a repair. Both the drain and that doctor path resolve targets through `storage/sessions.py`'s `_resolve_pending_target`, so they cannot disagree about where a session tag lands.

A third invariant governs the bookkeeping itself: **a valid conversation pointer is never discarded.** `ingested_files.conversation_id` is the only link from a source file to what it produced, so clearing it strands the conversation and — because a NULL pointer makes the next re-ingest skip its delete and collide again — freezes that file permanently. Every failure path rolls its transaction back first, which resurrects the conversation the re-ingest branch had already deleted, so "this run failed" is never evidence that nothing belongs to the path: the error is recorded and a pointer that still resolves is kept. Only a path that never produced a conversation records NULL. A store that failed *because* the conversation already exists does not route to the error writer at all; it re-points the row at that conversation.

Two corollaries fall out of that. **The row never asserts content it did not ingest**: the collision repair leaves `file_hash`/`file_mtime`/`file_size` at whatever was actually stored (a never-matching sentinel when there is no row) rather than stamping the bytes it just hashed for a conversation some other read produced — stamping them makes the unchanged-file skip match forever, which is a silent freeze dressed as a success. And **a row carrying an error is re-examined every run**, whatever its stat says, because the error write stamps the failing file's own stat; without that, a transcript that stops changing after a failure hides behind the skip and the self-heal below is unreachable for exactly the population that needs it.

Neither is the row believed on the way in. The re-ingest path re-derives the truth from the parsed conversation's `(harness_id, external_id)` rather than trusting a NULL, which is what lets rows poisoned by older versions heal themselves — and why that healing must snapshot tags first, since in the poisoned state the orphan is where the tags live. What it must not do is assume the conversation it finds is unowned: `conversation_id` has no uniqueness constraint and is `ON DELETE CASCADE`, so two paths can carry one session (a restored backup, an overlapping `--path`, or the collision repair's own re-link) and deleting that conversation would take the other path's row and its events with it. `_conversation_claimed_elsewhere` is the guard, and no site asks it directly: every replacement goes through `_take_conversation_for_replacement`, which guards, snapshots, and deletes as one operation and returns `None` to refuse. The three sites (the ordinary hash-changed replace, the session-strategy replace, the self-heal) differ only in what they do with a refusal, so "ask before replacing" is a property of the mechanism rather than a rule each site has to remember — which is what the hash-changed path forgot, destroying the sharing partner on the first content change. A duplicate copy is linked, warned about, and left settled rather than replaced: it records the bytes it has (so the copies do not churn and the warning fires once per change, not once per run) but its content is never ingested, because only the path holding the session's slot may write that conversation. Ingest runs under a per-database advisory lock (`api/ingest.py`) so the race that produced those rows cannot recur; a second concurrent invocation is a quiet no-op, not an error — and a filesystem that refuses the lock degrades to running unlocked with a warning, never silently.
